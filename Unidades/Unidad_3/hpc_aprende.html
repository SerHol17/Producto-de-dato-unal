💡 La gran lección
El paralelismo NO es gratis. Hay una parte del código que siempre debe ejecutarse de forma secuencial: inicialización, sincronización, lectura de disco, etc. Esta fracción determina el límite máximo de speedup, sin importar cuántos procesadores uses.

Dos leyes cuantifican esto: Amdahl (peor caso, problema fijo) y Gustafson (mejor caso, problema crece). Las dos tabs siguientes las exploran en profundidad.

🔵 PyTorch Distributed Training — Entrenamiento de LLMs
Al agregar más GPUs, los equipos de ML también aumentan el batch size y el dataset. El problema crece con los recursos. Esto es Gustafson: el tiempo permanece constante, pero se resuelve un problema MÁS GRANDE.
🔑 El insight clave: problema FIJO vs problema que CRECE
🔴 Problema FIJO (Amdahl)
Mismo dataset para todos los casos. Más GPU → menos tiempo. Pero la parte serial crea un techo.
🔵 Problema CRECE (Gustafson)
Más GPU → dataset más grande. El tiempo se mantiene. Pero resuelves MÁS trabajo.

💡 ¿Ves la diferencia? En Gustafson, el tiempo de ejecución (barra de tiempo = serial + 1 bloque por GPU) es constante, pero el problema total (todos los bloques azules) crece linealmente. Por eso el speedup de Gustafson supera el límite de Amdahl: estás midiendo cuánto MÁS TRABAJO haces, no cuánto más rápido vas.

🏭 ¿Cuándo usa cada ley la industria?
🔴 Amdahl — Strong Scaling
✅ Renderizar un video de duración fija
✅ Compilar un proyecto con N archivos fijos
✅ Correr un test suite de tamaño fijo
✅ Procesar un batch de datos ya definido
→ El problema NO crece con más hardware
🔵 Gustafson — Weak Scaling
✅ Entrenar con más datos al agregar GPUs
✅ Indexar más repos al escalar crawlers
✅ Analítica de streaming que crece con usuarios
✅ Simulaciones de mayor resolución/precisión
→ El problema SÍ crece con más hardware
